Plexus

AI agents that run inside your database, and get better from their own history.

Built on pg_synapse, pg-raggraph, stele and chunkshop. One Postgres.

Plexus is a demo of one idea: put the agent where the data already lives. Everything you will see runs inside a single Postgres. The only thing outside is the model.

A typical agent touches five systems

Every arrow is a place where a run can half-finish, disagree with the others, or leave nothing behind to explain it.

This is the shape of almost every agent demo. The agent lives in an app server, retrieval in a vector store, memory in a third service, and improvement in somebody's notebook. Five systems that each keep their own version of what happened.

Plexus puts all of it in one Postgres

Postgres
pg_synapseThe agent runtime. SELECT synapse.execute(...) runs the whole tool-calling loop in one transaction.
pg-raggraphVersioned retrieval. Documents carry effective dates, so you can ask what was true on a given day.
steleMemory with receipts. Every belief points at its evidence; a correction supersedes, it never erases.
chunkshopIngest for policy documents and for the agent's own past runs.
The modelThe only thing outside. Here, Qwen3.6 35B on a DGX Spark. It is a row in a table; swapping it is an UPDATE.
Four Postgres pieces. pg_synapse runs the agent, pg-raggraph does time-aware retrieval, stele is memory with evidence, chunkshop ingests. The model sits outside and is just configuration.

Hold the model fixed. Improve everything around it.

Google Research's harness2 calls the prompt, rules, tools and hints around a model its harness, and tunes that instead of the weights.

Lessons
  1. ProposeAn improver reads past runs and suggests edits: how the agent works, and what an expert in the domain would know.
  2. ProbeEach edit runs once against the real task, in its own throwaway copy of the database.
  3. ComposeThe best ideas are combined; the cheapest version that still passes every check is adopted.
  4. ReflectOne lesson is written down for the next round, citing the run it came from.
This is the part borrowed from harness2. Stop trying to make the model smarter. Treat everything around it as the thing you optimize, and do it with evidence from real runs.

Because the harness is data, the database can enforce a budget: always-on context is capped, and the tuner can only adopt an edit that fits. Skills and hints cost nothing until they are needed.

    harness2 is a good method; this is not a knock on it. It tunes offline and hands you files. Plexus runs the same loop where the work happens, so the result is a transaction, a veto and an update, not a pile of files to wire up.

    What it does not do yet

    • Model choice still matters. A 4B model tops out at 3 of 5 checks on this task. The 35B model passes; the tuner makes it cheaper.
    • The veto is an LLM call per insert. 5 to 10 seconds. Right for refunds, too slow for a hot write path.
    • Long runs sometimes quit early. The agent occasionally stops before every ticket is done. The checks catch it; the harness does not prevent it yet.
    • The dollar figures are assumptions. The wrong-policy rate in the business case is an input, not a measurement.
    Say these before someone else does. Each one is on the roadmap slide that follows.

    What we would build next

    Rules fast path in front of the vetoClear-cut refunds decided in milliseconds; the model only sees the borderline ones
    Harness version historyEvery adopted change reversible with one call
    Replay measurementRe-run old tickets with and without the date check, so the wrong-policy rate is measured
    Human approval queueBorderline refunds wait for a person, in the same transaction model
    Finish-the-job guardA run cannot end while a ticket it read is still undecided
    Each item closes one of the gaps on the previous slide. None of them needs a new system; they are tables and triggers.
